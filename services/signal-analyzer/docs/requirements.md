# Вимоги — Аналізатор якості зв'язку (Команда 2)

## 1. Мета

Консольна програма C++17, яка приймає навчальні вимірювання якості зв'язку (рівень сигналу, затримка, втрати пакетів), перевіряє їх, класифікує кожне як GOOD, DEGRADED або CRITICAL, обчислює середні значення та знаходить найгірше вимірювання з поясненням причини.

## 2. Межі системи

Входить у систему:

- введення вимірювань з клавіатури через меню;
- валідація кожного вимірювання до збереження;
- зберігання до 100 вимірювань у масиві;
- класифікація, середні значення, найгірше вимірювання, звіт.

Не входить у систему:

- реальні телекомунікаційні протоколи та мережа;
- читання з файлів, бази даних, GUI;
- передавання результатів іншим сервісам (лише описано як майбутня інтеграція, розділ 9).

## 3. Модель даних

```cpp
struct SignalMeasurement {
    int deviceId;              // ідентифікатор пристрою
    int signalLevel;           // рівень сигналу, dBm
    int latencyMs;             // затримка, мс
    double packetLossPercent;  // втрати пакетів, %
};

enum class SignalClass { GOOD, DEGRADED, CRITICAL };

const int MAX_MEASUREMENTS = 100;
SignalMeasurement measurements[MAX_MEASUREMENTS];  // у main, не глобально
int measurementCount = 0;                          // 0..MAX_MEASUREMENTS
```

| Поле | Тип | Допустимий діапазон | Примітка |
|---|---|---|---|
| `deviceId` | `int` | 1 … 9999 | один пристрій може мати кілька вимірювань |
| `signalLevel` | `int` | −150 … 0 | dBm, ціле число |
| `latencyMs` | `int` | 0 … 5000 | мілісекунди, ціле число |
| `packetLossPercent` | `double` | 0.0 … 100.0 | відсоток |
| `measurementCount` | `int` | 0 … 100 | кількість збережених записів |

Клас вимірювання (`SignalClass`) не зберігається у структурі, а обчислюється функцією `classifySignal` під час виведення. Так клас завжди відповідає поточним правилам.

## 4. Порогові значення (константи)

| Константа | Значення | Правило |
|---|---|---|
| `CRITICAL_SIGNAL` | −100 | CRITICAL, якщо `signalLevel < -100` |
| `CRITICAL_LATENCY` | 300 | CRITICAL, якщо `latencyMs > 300` |
| `CRITICAL_LOSS` | 20.0 | CRITICAL, якщо `packetLossPercent > 20` |
| `DEGRADED_SIGNAL` | −85 | DEGRADED, якщо `signalLevel < -85` |
| `DEGRADED_LATENCY` | 150 | DEGRADED, якщо `latencyMs > 150` |
| `DEGRADED_LOSS` | 5.0 | DEGRADED, якщо `packetLossPercent > 5` |

Порівняння строгі: значення, що точно дорівнює порогу, **не** переходить у гірший клас. Наприклад, `signalLevel = -100` — це DEGRADED, а не CRITICAL; `latencyMs = 150` — це GOOD.

## 5. Функціональні вимоги та критерії приймання

### FR-2.1 Введення до 100 вимірювань

Користувач обирає в меню «Додати вимірювання» і вводить чотири значення: `deviceId signalLevel latencyMs packetLossPercent`.

Критерії приймання:

- коректне вимірювання додається, `measurementCount` збільшується на 1;
- якщо вже збережено 100 вимірювань, програма виводить повідомлення «Сховище заповнене» і не змінює масив;
- нечислове введення (наприклад `abc`) не завершує програму аварійно: виводиться помилка, введення очищується, програма повертається в меню.

### FR-2.2 Перевірка допустимих діапазонів

Кожне поле перевіряється функцією `validateMeasurement` **до** збереження.

Критерії приймання:

- значення поза діапазонами з розділу 3 відхиляються з повідомленням, яке поле некоректне. Приклади відхилених значень:
  - `deviceId = 0` → «deviceId має бути від 1 до 9999»;
  - `signalLevel = 5` → «signalLevel має бути від -150 до 0»;
  - `signalLevel = -151` → «signalLevel має бути від -150 до 0»;
  - `latencyMs = -1` → «latencyMs має бути від 0 до 5000»;
  - `packetLossPercent = 150` → «packetLossPercent має бути від 0 до 100»;
- відхилене вимірювання не потрапляє в масив, `measurementCount` не змінюється;
- некоректні числа не класифікуються і не враховуються в середніх значеннях.

### FR-2.3 Класифікація GOOD / DEGRADED / CRITICAL

Функція `classifySignal` перевіряє правила **саме в такому порядку**:

1. якщо `signalLevel < -100` або `latencyMs > 300` або `packetLossPercent > 20` → CRITICAL;
2. інакше, якщо `signalLevel < -85` або `latencyMs > 150` або `packetLossPercent > 5` → DEGRADED;
3. інакше → GOOD.

Критерії приймання:

- `-101, 50, 0` → CRITICAL (через рівень сигналу) — контрольний приклад із завдання;
- `-100, 50, 0` → DEGRADED (точний поріг CRITICAL не спрацьовує);
- `-85, 150, 5` → GOOD (усі значення рівно на порозі DEGRADED);
- `-70, 300, 20` → DEGRADED (latency і loss рівно на порозі CRITICAL, тому CRITICAL не спрацьовує, але `300 > 150` і `20 > 5` дають DEGRADED);
- `-70, 400, 0` → CRITICAL (через затримку).

### FR-2.4 Середні значення

Функція `calculateAverages` обчислює середні `signalLevel`, `latencyMs` і `packetLossPercent` за всіма збереженими вимірюваннями.

Критерії приймання:

- для вимірювань `-80, 100, 2` і `-90, 200, 4` середні: `-85.0`, `150.0`, `3.0`;
- якщо `measurementCount == 0`, програма виводить «Немає даних для обчислення» і **не ділить на нуль**.

### FR-2.5 Найгірше вимірювання та причина

Функція `findWorst` повертає індекс найгіршого вимірювання:

1. гіршим вважається вимірювання з гіршим класом: CRITICAL > DEGRADED > GOOD;
2. якщо клас однаковий — гірше те, у якого більші `packetLossPercent`;
3. якщо й це однакове — залишається те, що введене раніше.

Причина (функція `explainReason`) — перше правило, яке спрацювало для цього класу, у порядку перевірки: рівень сигналу → затримка → втрати. Для GOOD причина — «усі показники в межах норми».

Критерії приймання:

- для набору `(1: -70, 50, 1)`, `(2: -101, 50, 0)`, `(3: -90, 100, 2)` найгіршим є вимірювання пристрою 2, причина «рівень сигналу -101 < -100»;
- якщо `measurementCount == 0`, виводиться «Немає даних», функція повертає `-1`, звернення до масиву не відбувається.

## 6. Меню

```text
=== Signal Analyzer ===
1. Додати вимірювання
2. Показати всі вимірювання з класом
3. Середні значення
4. Найгірше вимірювання
5. Повний звіт
0. Вихід
```

Повний звіт містить кількість вимірювань, кількість кожного класу, середні значення та найгірше вимірювання з причиною. Неіснуючий пункт меню (наприклад `7` або `x`) виводить повідомлення про помилку і повертає в меню.

## 7. Нефункціональні вимоги

- мова C++17, лише стандартна бібліотека;
- збірка без попереджень: `g++ -std=c++17 -Wall -Wextra -pedantic src/main.cpp -o app`;
- жодних глобальних змінних — масив і лічильник створюються в `main` і передаються у функції параметрами;
- усі порогові значення та ліміти задані через `const`;
- індекс масиву завжди в межах `0 … measurementCount - 1`.

## 8. Архітектура та функції

| Компонент | Функції | Відповідальність |
|---|---|---|
| Input | `readMeasurement`, `readMenuChoice` | зчитування значень і пункту меню, обробка нечислового введення |
| Validation | `validateMeasurement` | перевірка діапазонів полів |
| Processing | `classifySignal`, `calculateAverages`, `findWorst`, `explainReason` | правила класифікації, середні, найгірше вимірювання |
| State | `addMeasurement`, масив `measurements`, `measurementCount` | збереження вимірювань із контролем межі масиву |
| Report | `printMeasurements`, `printAverages`, `printWorst`, `printReport` | формування результату |
| Main | `main`, `printMenu` | цикл меню та виклик функцій |

### Псевдокод головного алгоритму

```text
ПОЧАТОК
  measurementCount ← 0
  ПОВТОРЮВАТИ
    вивести меню
    choice ← readMenuChoice()
    ЯКЩО choice некоректний → вивести помилку, ПРОДОВЖИТИ
    ВИБІР choice:
      1: ЯКЩО measurementCount == MAX_MEASUREMENTS → «Сховище заповнене»
         ІНАКШЕ
           ЯКЩО readMeasurement(m) не вдалося → «Некоректне введення»
           ІНАКШЕ ЯКЩО validateMeasurement(m) == false → вивести поле з помилкою
           ІНАКШЕ addMeasurement(measurements, measurementCount, m)
      2: printMeasurements(...)          // для кожного: classifySignal
      3: ЯКЩО measurementCount == 0 → «Немає даних»
         ІНАКШЕ calculateAverages(...) і printAverages(...)
      4: worst ← findWorst(...)
         ЯКЩО worst == -1 → «Немає даних» ІНАКШЕ printWorst(... explainReason ...)
      5: printReport(...)
  ПОКИ choice ≠ 0
КІНЕЦЬ
```

## 9. Майбутня інтеграція (не реалізується)

У майбутньому сервіс зможе передавати вимірювання класу DEGRADED і CRITICAL як події сервісам 4 (Черга подій), 5 (Менеджер інцидентів) і 8 (Операційний звіт) у форматі:

```text
EVENT;<id>;SIGNAL;<GOOD|DEGRADED|CRITICAL>;device-<deviceId>
```

Зараз ця інтеграція не реалізується і на контекстній діаграмі позначається пунктиром.
