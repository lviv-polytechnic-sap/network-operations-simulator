## 3. Вхідні й вихідні дані

### Вхідні дані (від користувача в консольному меню)
- **Команда меню:** ціле число (`1` — додати інцидент, `2` — показати відкриті, `3` — закрити за ID, `0` — вихід).
- **Поля нового інциденту (`Incident`):**
  - `id` (`int`) — унікальний цілий ідентифікатор інциденту (`id > 0`);
  - `source` (`std::string`) — непорожній ідентифікатор мережевого джерела (наприклад, `router-1`);
  - `category` (`std::string`) — одна з допустимих категорій: `SIGNAL`, `OVERLOAD`, `DEVICE_OFFLINE`, `DATA_ERROR`;
  - `severity` (`std::string`) — один із допустимих рівнів критичності: `INFO`, `WARNING`, `CRITICAL`.
- **Ідентифікатор для закриття:** ціле число `id` наявного відкритого інциденту.

### Вихідні дані (консольний вивід та внутрішній стан)
- **Стан сховища (`Incident Storage`):** збережені структури `Incident` у статичному масиві (`MAX_INCIDENTS = 100`) із полем стану `resolved` (`false` — відкритий, `true` — закритий).
- **Повідомлення користувачеві:**
  - підтвердження додавання, автоматичної ескалації (`WARNING -> CRITICAL`) або закриття інциденту;
  - відформатований список усіх активних (`resolved == false`) інцидентів із підсумковими лічильниками (`Open incidents` та `Total incidents`);
  - повідомлення про помилки валідації, переповнення сховища або спробу закрити неіснуючий / вже закритий інцидент.

## 4. Правила та відомі обмеження

### Бізнес-правила
- **Валідація:** будь-який запис із нечисловим або недодатним `id`, дублікатом `id`, порожнім `source`, невідомою категорією чи рівнем критичності відхиляється без зміни стану сховища.
- **Автоматична ескалація:** під час додавання нового інциденту рівня `WARNING` підраховується кількість відкритих (`resolved == false`) інцидентів `WARNING` із тим самим `source` (включно з новим). Якщо кількість дорівнює `3`, **саме новому** запису автоматично встановлюється рівень `CRITICAL`. Попередні два записи залишаються `WARNING`.
- **Облік закритих інцидентів:** закриті інциденти (`resolved == true`) не враховуються у лічильнику попереджень при ескалації та не можуть бути закриті повторно.

### Відомі обмеження
- **Фіксована ємність пам'яті:** максимальна кількість інцидентів обмежена константою `MAX_INCIDENTS = 100` (без динамічного розширення).
- **Відсутність персистентності:** дані зберігаються лише в оперативній пам'яті під час сесії роботи програми та не записуються у файл або базу даних після завершення.
- **Технічні обмеження:** використовується виключно стандартна бібліотека **C++17**, заборонені глобальні змінні, однопотоковий консольний інтерфейс.

## 6. Збірка та запуск

### Локальна збірка та запуск
1. Переконайтеся, що встановлено компілятор із підтримкою **C++17** (`g++` або `clang++`).
2. Перейдіть у каталог сервісу `services/incident-manager/` та скомпілюйте програму:

```bash
g++ -std=c++17 -Wall -Wextra -pedantic src/main.cpp -o incident_manager
```

3. Запустіть зібраний виконуваний файл:
   - **Linux / macOS:**
     ```bash
     ./incident_manager
     ```
   - **Windows (CMD / PowerShell):**
     ```powershell
     incident_manager.exe
     ```

### Docker
Docker у цьому сервісі **не використовується** (сервіс є автономним консольним застосунком на C++17 без зовнішніх залежностей).

## 7. Контрольні приклади

### Приклад 1: Автоматична ескалація 3-го відкритого `WARNING`
**Вхідні дії (послідовний вибір пункту `1. Add new incident`):**
1. `ID = 1`, `source = router-1`, `category = SIGNAL`, `severity = WARNING`
2. `ID = 2`, `source = router-1`, `category = OVERLOAD`, `severity = WARNING`
3. `ID = 3`, `source = router-1`, `category = DATA_ERROR`, `severity = WARNING`

**Очікуваний результат у консолі:**
```text
Escalation: 3rd open WARNING for source 'router-1'. Severity automatically upgraded to CRITICAL.
Incident validated and added successfully (total: 3).

--- Open Incidents ---
ID: 1 | Source: router-1 | Category: SIGNAL | Severity: WARNING
ID: 2 | Source: router-1 | Category: OVERLOAD | Severity: WARNING
ID: 3 | Source: router-1 | Category: DATA_ERROR | Severity: CRITICAL
Open incidents: 3 | Total incidents: 3
```

### Приклад 2: Закриття інциденту та виключення його з лічильника ескалації
**Вхідні дії (продовження роботи після Прикладу 1):**
1. Обрати `3. Close incident by ID` і ввести `1`.
2. Повторно обрати `3. Close incident by ID` і ввести `1`.
3. Обрати `1. Add new incident` і додати: `ID = 4`, `source = router-1`, `category = DEVICE_OFFLINE`, `severity = WARNING`.

**Очікуваний результат:**
- Крок 1: `Incident ID 1 has been closed.`
- Крок 2: `Incident ID 1 is already closed.`
- Крок 3: ескалація не відбувається (відкритих `WARNING` для `router-1` тепер два: `ID 2` та `ID 4`), запис `ID 4` додається зі статусом `Severity: WARNING`.

## 9. Контракт майбутньої інтеграції

Сервіс спроєктовано як ізольований модуль обробки подій із чітко визначеною моделлю даних, готовий до подальшої інтеграції з іншими компонентами симулятора мережевих операцій (модулем моніторингу топології, диспетчером подій або панеллю оператора) без зміни поточної реалізації ядра.

- **Формат передачі вхідної події:** зовнішній модуль моніторингу формує структуру події з обов'язковими полями `id` (`int > 0`), `source` (`std::string`), `category` (`SIGNAL | OVERLOAD | DEVICE_OFFLINE | DATA_ERROR`) та `severity` (`INFO | WARNING | CRITICAL`).
- **Обробка та збагачення стану:** ядро сервісу виконує валідацію вхідного пакету, перевірку переповнення сховища (`MAX_INCIDENTS = 100`) та застосовує правило ескалації для повторюваних попереджень з одного джерела, повертаючи підтвердження реєстрації або код/повідомлення помилки валідації.
- **Інтерфейс отримання активних інцидентів та зміни стану:** панель оператора або модуль алертингу запитує зріз активних записів (`resolved == false`) та ініціює зміну життєвого циклу інциденту (`resolved: false -> true`) за унікальним ключем `id`.
